## Next interruption capture: execution and waiting contract

The verification client owns one child server process, its stdin/stdout handles and the official SDK session. Explicit cancellation sends an SDK-serialized `notifications/cancelled` for its owned tool request ID and keeps the session open. Disconnect closes the child server's stdin without first canceling the SDK call or disposing its session; the server must exit naturally while the Revit callback is still held. Use SDK `StreamClientTransport` over these owned process streams to make that EOF boundary explicit. SDK typed request/message APIs own serialization, metadata and dispatch; no MCP transport implementation is copied or hand-written. This uses the existing C# SDK 2.2.0 package; TypeScript 1.26.0 remains precedent-only. Initial token-only cancellation probes canceled the local wait but contained no wire cancellation and failed server invalidation. Preserve those failures: this explicit-notification test establishes a different stimulus, not closure of the token-only observation.

An independent observer waits for the actual host's held marker before requesting interruption. It must see immediate invalidation **before the original deadline**, while executor exit/quiescence remain absent. Only then does it release the hold, await executor/quiescence and open the verification client's finish gate. Cancellation retains a connected catalog check and three-second no-late-success window; EOF records natural server exit before release and retains the ended connection's wire. A new SDK process subsequently proves recovery. The 45-second diagnostic safety release and original 30-second request budget remain unchanged. Failed preconditions, timeout, forced child termination or automatic host release are failed captures, never acceptance. The observer owns only its exclusive arm/release files; borrowed callbacks and physical lifetime disposal remain outside its claims.

Keep cancellation, EOF, Stop and application shutdown separate: these operations have different progress dependencies.

## Execution and waiting model

The approved host checklist permits diagnostic instrumentation. A timeout response alone does not establish whether a reader later starts. These controls observe the existing production flow without replacing its queue, context validation, budget or reader.

| Boundary | Execution owner and observation | Allowed waiting |
|---|---|---|
| Admission | Endpoint wrapper records original request ID and attaches observers to the original Response/Quiesced tasks | No wait for observers; no registrations on the private transport signal |
| Preparation | API executor captures and validates context, then optionally holds before returning from preparation | At most 45 seconds, or explicit release; the original request deadline keeps running |
| Final read guard | Unchanged `ReadinessExecutionFlow` checks the same context after preparation | No diagnostic replacement of this guard |
| Started reader | Actual reader records entry, initializes its report using Autodesk data, then optionally holds | Same bounded hold; already-started reads may finish, but the original post-read/publication guards still apply |
| Cancellation | Recorder polls authoritative invalidation/expiry, without running borrowed callbacks | Observation only; it does not cancel, reset or extend the request |
| Stop during a callback | An explicitly armed diagnostic control invokes the existing Stop in valid API context, then holds the callback | Network progress must be independent of the held callback; this is injected Stop, not a human click during blocked UI |
| Native events | Observe Raise begin/result, API disposal, hook/unhook, application shutdown | No waits added to native event ownership |
| Retirement | Observe original Response, Quiesced and network-stop tasks separately | Observer work is not part of those tasks' completion; physical lifetime disposal is not inferred from Quiesced |

Control files are local test inputs, never MCP arguments. Each stage arm is consumed once; release files are bound to that request and stage. A stale release file makes the control invalid rather than immediately passing a hold. Missing release automatically unblocks by the diagnostic limit. Invalid controls are recorded and do not hold execution. The recorder has a bounded event count; missing/truncated/error evidence cannot pass acceptance. No model write, transaction or export is added.

First demonstrate the controls offline, including cancellation during held preparation and a simulated started reader, unchanged deadline, stale release rejection and bounded automatic release. Then identify diagnostic source/binary hashes and capture live tests, including the actual reader and asynchronous endpoint observations. A diagnostic pass is not a normal-build desktop A8 pass. Restore the normal build before final sample/client acceptance. Retain failed attempts and list native outcomes that could not be observed.

The agent writes `arm-Preparation.txt` or `arm-Reader.txt` inside that PID directory. Exactly two lines specify milliseconds (`1` through `45000`) and mode (`hold` or `stop`). Each arm is moved to `used-<request-id>-<stage>.txt` when consumed by the next information-check request; context-acquisition calls never consume it. `held-<request-id>-<stage>.txt` retains the original UTC deadline. Create `release-<request-id>-<stage>.signal` to release the hold early. The injected Stop mode calls the existing bridge Stop on the API thread before holding. It does not terminate Revit or invoke application shutdown.

`events.tsv` has nine columns: sequence, UTC, monotonic timestamp, managed thread ID, stage, original request ID, cancellation state, expiry state, detail. Important stages are Submitted, ExecutorEntered/Exited, ReaderEntered/Exited, GateHeld/Released, AutomaticRelease, InactiveObserved, ResponseCompleted, QuiescedObserved, NetworkStopped, NativeRaiseBegin/End, EventDisposed, EventsHooked/Unhooked and ApplicationShutdownEntered/Returned. Response/Quiesced observers are asynchronous: their record order is not proof of exact task-completion order. Missing expected stages, ControlRejected, a diagnostic-error.txt file, automatic release where explicit release was required, or the recorder's event limit make that intended capture invalid.
