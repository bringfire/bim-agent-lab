## Test driver before live use

The new verification-only `interrupt` scenario owns a child production server and gives its stdin/stdout streams to official SDK **2.2.0** `StreamClientTransport`. For explicit cancellation it sends a typed SDK tool request with an owned RPC ID, then an SDK-serialized `notifications/cancelled` for that ID. For EOF it closes server stdin before disposing the SDK or requesting cancellation. The SDK still owns discovery, metadata, serialization, correlation and protocol dispatch. No MCP transport is implemented by hand; no SDK implementation is copied. TypeScript SDK 1.26.0 remains precedent-only. No dependency, production source, installation or client settings changed.

The six new offline cases use the actual production executable and real Windows pipes with a held synthetic executor. They cross cancellation/EOF with `2025-06-18`, `2025-11-25`, and `2026-07-28`. Initially all six failed because the old driver rejected the new scenario. The first implementation passed all three EOF cases but failed all three token-cancellation cases. The client's local wait threw `TaskCanceledException`, but the captured traffic contained **no cancellation notification**, and the endpoint context stayed active. Do not erase those failures or interpret a locally canceled wait as remote cancellation.

The exact cause of that token-only observation is **not established**. Pinned source was inspected, including SDK [cancellation registration](https://github.com/modelcontextprotocol/csharp-sdk/blob/6fa3825973949a9c4f0cd8af344e15a8db09dc35/src/ModelContextProtocol.Core/McpSessionHandler.cs) and [stream client transport](https://github.com/modelcontextprotocol/csharp-sdk/blob/6fa3825973949a9c4f0cd8af344e15a8db09dc35/src/ModelContextProtocol.Core/Client/StreamClientTransport.cs). The deliberate explicit-notification stimulus tests the server/bridge cancellation contract; it does **not** fix or close token-only SDK propagation. The failing form was `client.CallToolAsync(..., cancellationToken: callCancellation.Token)`, followed by `callCancellation.Cancel()` after actual pipe admission. The retained [first implementation log](host-interruption-evidence/interrupt-driver-green.txt) and [raw attempts](host-interruption-evidence/hashes.json) preserve that distinction.

After the explicit-message change, all **six driver tests pass**. They require the same original deadline, rejection by the final-read guard while more than 15 seconds remain, held Response/Quiesced tasks, EOF server exit before executor release, a live server for cancellation, and no cancellation message in the EOF traffic. The verification client keeps a finish gate and three-second observation window; forced recovery of its owned child process fails acceptance. ## Actual queued requests

One actual reader was held to keep the API executor occupied. Three additional requests used the already-acquired context and were admitted sequentially into the production queue, then subjected to explicit cancellation, EOF, and deadline expiry. Captured `Submitted` records establish admission while the blocking reader was held. Each queued request has **zero executor entries and zero reader entries**. All three `Quiesced` observations occurred before releasing that reader. The cancellation/EOF cases quiesced while the blocker's later deadline still had over 15 seconds remaining, so expiry cannot substitute for those stimuli.

The blocker and the queued deadline request both returned `DeadlineExceeded`. After explicit release, the already-started blocker finished without late success. Connected clients retained their three-second catalog observation; the EOF server had already exited. A subsequent fresh report again matched the baseline. ## Stop during an actual read

The diagnostic `stop` arm invoked the unchanged `BridgeApplication.Stop` on Revit's API thread after actual reader entry, then held that callback. This is an **injected native Stop**, not application shutdown or a user clicking during blocked UI.

The trace records `StopEntered`, canceled Response, closed request connection, `NetworkStopped:RanToCompletion`, `EventDisposed`, `EventsUnhooked`, and `StopReturned` **before the held reader was released**. Disposal/unhook/Stop events occurred on Revit's startup/API thread. The descriptor was absent afterward and Revit remained alive. The client returned correlated retryable `BridgeUnavailable`; the connected SDK catalog still worked after release, with no late success. The reader then exited and the original Quiesced task was observed. A new SDK process independently returned `BridgeUnavailable` while the bridge was stopped.

External-event disposal is observed here; **physical request-lifetime disposal is not**. Do not combine those resource owners into one cleanup claim. Application shutdown, queued Stop, an in-flight native Raise at final shutdown, and every possible native Raise outcome remain separate observations. Earlier captures observed Accepted/Pending; Denied/TimedOut are not claimed.
