The point: knowing that you should ask for cloning and checkpoints, and why. The agent does the mechanics.

What you are asking the agent to do

A project lives on GitHub. Ask the agent to:

CloneMake a local copy so it can inspect the code.
BranchName a line of work; existing work stays safe.
Diff, then commitShow exactly what changed, then record a checked checkpoint. Its ID names that exact version.
PushSend commits to the remote. Publishing is a separate decision.

Four clicks: clone, branch, diff and commit, push. Handout page 3 has the full table, including remote and commit ID.

The branch name and diff are illustrations. Stress the difference between a commit (a local checkpoint) and a push (publishing). Publishing should be a separate, deliberate instruction.

Four clicks, one term each, after the quote. The author went on: SDKs, APIs, required libraries, dependencies, and GitHub repositories that might serve as precedents, "or as starting points if they have the proper license structure."

Participants don't need every package name in advance. They need to ask what role each resource plays.

Research and collect

Our agent investigated official Revit resources, local software and samples, and seven source repositories, cloned at recorded commits.

The agent recorded exact versions, relevant code, dependencies and license evidence. The research did not commit us to installing every tool or copying a particular bridge.

Reading the source changed the plan

An existing tool's query looked only at the current view and stopped at 100 elements by default.

A partial list can look like a whole model.The project description didn't mention the limit. Reading the code did.
So our report says what it examined.Requested and examined counts, plus two completeness flags.

Two clicks. The dot field is an illustration: that tool was never run on our sample. It shows what a 100-element default would mean for a model this size.

This is why we ask the agent to clone and read code, not just summarize a README. The finding shaped the whole design: our results report requested versus examined counts and two completeness flags.

Other findings from the same research (handout page 3, research story): Revit API libraries and samples were already installed; candidate tools brought different packages, runtimes and license terms; some repositories had source components that were not downloaded.

Consume, adapt, or learn from

Ask the agent to say which, for every resource it brings in.

License labels are evidence to review, not a blanket conclusion that everything may be redistributed.

Three clicks, one relationship each. A dependency ships with your tool and brings its own dependencies. Adapted code needs attribution and its license terms kept. A precedent costs nothing to ship but still has to be checked.

The repository's THIRD_PARTY_NOTICES file records what we consume and adapt. Everything else in the project is original lab code.

  and docs/how-to/.

  tests, and samples: projects/<project>/.
- Event-specific planning and
  presentations: workshops/<event>/.

## How to work
1. Inspect the repository, current branch,
   and existing changes before editing.
   Preserve unrelated work.

Agents start each session without memory. AGENTS.md (or CLAUDE.md) gives every session the same rules:

  • Purpose, audience and scope
  • Where each kind of work belongs
  • How to work: research, verify, commit
  • Commands and boundaries: what not to touch

Here, CLAUDE.md simply points to AGENTS.md, so Claude Code and Codex read the same instructions.

Long-term memory is part of the Monday-morning workflow: write it before the first build, and update it as decisions are made.

Our AGENTS.md also carries current status and safety boundaries, such as "no installer while Revit is open". It grew with the project.

Quick route: Dynamo

The agent writes the script; you run it in the correct Revit environment.

  1. Open a disposable sample project. Manage › Visual Programming › Dynamo; create a new graph.
  2. Set run mode to Manual. Place a Python Script node, select CPython3 and open its editor.
  3. Paste the two lines. Connect OUT to a Watch node and click Run.
import sys
OUT = ["Dynamo is working", sys.version]

Dynamo is included with Revit 2024, and its CPython3 engine has its own Python runtime. Next, ask for a read-only wall/ceiling inventory and compare its count with a native schedule.

Handout page 4. This only reports the Python version: a smoke check that the environment runs. It is not a rehearsed inventory script.

Ask the agent to confirm your installed Revit, Dynamo and engine versions first.

Quick route: pyRevit

A separate, optional add-in that runs Python scripts as ribbon buttons.

  1. Ask the agent to inspect the installed pyRevit version and Python engine, then create a small extension with a read-only script.py command.
  2. Have it give the exact registration and reload steps for that version. Run the button on the same sample and verify the output.

Dynamo and pyRevit use different host objects and may use different Python engines. Don't assume one script works in both.

pyRevit is not a prerequisite for following the seminar. These quick routes come before the compiled-plugin build: try one small read first.
