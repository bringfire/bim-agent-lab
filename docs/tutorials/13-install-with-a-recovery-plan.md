# Ask the agent to make installation recoverable

## How we engaged the agent

After the author relayed independent Task 6 closure, the next direction was simply: “ok, let's keep going”. That continued an already approved plan and Native execution choice. It did not require reopening the earlier client, SDK or architecture decisions. The next task was to install the bridge without losing the working readiness and Excel commands if installation stopped halfway through.

The important preparation came from earlier independent review. The reviewer had found that knowing the desired final files was insufficient: recovery information needed to exist before the first write. The author asked for the common missing concept behind several findings. That gave this task a concrete obligation to carry forward.

## What we asked the agent to prove

An installer can appear correct when every copy succeeds. We needed to know what happens after only one copy succeeds, after an obsolete file is removed, or after the fixture's shared library changes but its inventory does not. Recovery itself can be interrupted too.

The agent wrote an operation model before implementation and checked the existing installer. It found that fixture validation happened after readiness files had already changed. The new sequence prepares the whole change and all original backup bytes first. The test's expected answer is the original files and inventories, recorded before installation; it is not an answer generated by the recovery code.

Suggested prompt for participants, based on the approved review direction rather than a verbatim author instruction:

> Before touching the working installation, show what is already saved if the installer stops after its first write. Test interruptions between the important steps, then recover in a new process twice. Compare the original bytes and inventories, preserve unrelated files, and show what happens if someone edits a file before recovery.

## Keep the evidence separate

The first test run deliberately failed against unimplemented installer functions. A later run exposed a PowerShell conversion issue in atomic replacement. The agent traced that failure, corrected it and retained the failed runs. Passing a disposable installation test is useful evidence; it does not mean Revit loaded the add-in or that an agent received a correct model report.

The [technical procedure](../../projects/revit-readiness/docs/mcp-bridge-setup.md) gives future agents the exact paths, commands, ownership rules and recovery states. The [operation model](../explanation/recoverable-readiness-installation.md) explains the guarantees being tested. Live Revit observations and independent review must be recorded separately as they happen.

## Why the earlier research and records mattered

Inspection found that the actual fixture installation was older than its inventory mechanism. The agent did not simply label every existing file as owned. It compared the DLL hashes with the repository's earlier verification records and added a narrowly checked migration for that known version. A test confirms that undo restores the original state, including the absence of an inventory; an unknown version is rejected before any installed-file change. This is a practical reason to keep source versions and evidence from earlier lessons: they can resolve a later installation question without guessing.

## Ask for proof on the real machine too

After the disposable tests passed, the agent installed the bridge, undid it twice in separate processes and compared the real installation with its original 59-file snapshot. Every original hash and folder inventory matched. It then reinstalled and checked Revit: loading stayed inactive, Start twice reused a session, Stop removed it, and restart created a new session. A disposable complete-model copy produced the first live readiness report without changing its reported modified state.

The [live record](../../projects/revit-readiness/docs/verification/2026-10-21-live-installation.md) keeps those observations separate from tests that remain to be done. For participants, the useful follow-up is: **“Which claims have now been demonstrated in the real application, and which are still supported only by simulations or source inspection?”** Successful installation and one report are milestones; they do not answer every cancellation, document-change or desktop-client question.

## Ask whether the test reached the intended situation

One attempted family-document check returned a timeout. The automation had failed to finish opening the family, leaving Revit's Open dialog in place. The agent kept the failed attempt, confirmed the actual screen state and reran the check after the family loaded. The expected unsupported-document error then passed. Changing the plugin to satisfy the first attempt would have fixed the wrong problem.

A separate modal-dialog test correctly returned a timeout and allowed a later request. That still did not show whether an expired request could enter the reader after the dialog closed: the original client had already disconnected. We kept that stronger claim open. This carries the earlier review lesson into application testing: evidence for one part of an operation is not proof of its entire lifetime.

Suggested participant follow-up:

> Show that the test reached the situation we intended. Which observation proves the claim, and which part remains unobserved? Keep failed attempts, explain the retry, and don't count an error message as proof of cleanup or cancellation inside the application.

## Ask what else could explain a passing result

The author completed the manual Save As and replied, “BAL-info-saved-as is now saved.” The agent verified the new file and document lifetime. But the earlier context token had already expired: rejecting it could be explained by expiry alone. We kept the narrower result and left the specific Save As invalidation check open. A useful test must distinguish the explanation we intend to prove from other explanations that fit the same result.

The agent then changed one type value in the disposable model through Revit, reused the earlier token and confirmed that the report contained the new value. A query made after the change is evidence of fresh data only if we compare the actual value. The first attempt to undo the test edit did not restore it; a second report exposed that. Closing without saving the temporary edit and reopening restored the saved baseline. The manual JSON, text and four-sheet Excel outputs were also compared with the MCP result.

For shutdown, the agent connected clients that had sent incomplete input. Stop closed those connections promptly. A separate control deliberately omitted Stop: those connections eventually closed through their ordinary timeout. The observer correctly refused to count that as a Stop result. The first observer also checked session cleanup too early, at connection closure; it was corrected to observe the two stages separately. This applies the review lesson to tests themselves: a test can contain a mistaken model of an operation's lifetime too.

Suggested follow-up for participants:

> What other explanation could produce this result? Add a control that separates those explanations. Confirm that our test fails when the behavior we want to prove does not happen, and record any limits on the claim.

The [technical guide](../../projects/revit-readiness/docs/mcp-bridge-setup.md) explains the timing controls and retained evidence. These observations advance Task 7; they do not close the remaining instrumented cancellation checks or either desktop application's final acceptance.

## Let the person operate the application when that helps

The author asked: “what do you need me to do to facilitate this, rather than you trying to use ‘computer use’ to accomplish this task?” We changed the division of work. The person operated Revit; the agent prepared the test, sent requests and checked the results. Participants do not need to learn a terminal interface to help verify their plugin.

The author first replied “ready for save as test”. Only then did the agent acquire the five-minute context, confirm the active model, and give one instruction: save the disposable model under a specific new name, leave it active, and reply “saved”. The matching checklist had already been prepared. This kept setup time out of the short test window.

After “saved”, the agent checked the original token immediately. Revit rejected it with `ContextChanged`, more than three minutes before expiry. A fresh context returned a complete report for the new file with the same project identity, a different document lifetime, 16 examined instances and zero findings. The earlier expired attempt remains in the record; this second attempt supplies the evidence it lacked.

Suggested participant prompt, not a verbatim instruction from this session:

> Prepare the test and tell me one application step at a time. Wait until I am ready before starting any time-limited check. I will operate Revit and report when the step is done; you verify the actual state through the plugin, preserve the evidence and explain what it proves.

The useful boundary is responsibility, not whether every action is automated. A person's “saved” response triggers verification; the returned model identity and report establish the observed result. See the [agent procedure](../../projects/revit-readiness/docs/mcp-bridge-setup.md#coordinate-a-human-operated-save-as-test) and [fresh-token evidence](../../projects/revit-readiness/docs/verification/2026-10-21-live-installation.md#coordinated-fresh-token-save-as).

## Ask the agent to make an unobserved claim testable

After the person closed Revit, the agent verified shutdown and recorded the saved file's hash. The next question came from the existing plan: a timeout message tells us the caller stopped waiting, but did the plugin subsequently begin reading anyway? Answering that requires observing the reader inside Revit.

The agent prepared a separate diagnostic build that can pause at specific boundaries and record what actually happens. Its normal deadline and safeguards remain in place. The person only needs to open the disposable model and start the bridge; the agent controls the test pauses and releases. Tests of those controls come before installing the diagnostic build, and the recoverable installer preserves the normal build for restoration. A diagnostic observation and a successful seminar demonstration remain separate milestones.

Suggested participant prompt:

> If our current evidence cannot prove the claim, explain what we need to observe. Prepare a bounded diagnostic test, show how we return to the normal plugin, and distinguish tests of the diagnostic controls from results inside Revit.

The [diagnostic procedure](../../projects/revit-readiness/tests/host-diagnostics/README.md) gives agents the execution model, commands, file formats and limits. The source and logs should make it possible for a reviewer to distinguish an actual reader entry from an inferred one.

## Report the failure and keep the agent's explanation accountable

The author next sent a screenshot with “getting this”. Revit could not start the temporary diagnostic add-in because it could not read a test configuration file. The agent found the file present and verified that the installed diagnostic code could read it outside Revit. That narrowed the investigation, but did not explain the failure inside Revit. No readiness check had run.

The useful response is to separate observation from explanation: preserve the error, identify what failed, state what remains unknown, and give the person one application step at a time. A successful retry would show recovery; it would not, by itself, prove the cause was understood or corrected.

Suggested participant prompt:

> Here is the actual error. Explain which part failed and what your evidence establishes. Preserve the failed attempt, tell me the next manual step, and do not call the issue fixed just because it works outside the application or on a retry.

The [investigation record](../../projects/revit-readiness/docs/verification/2026-10-21-host-diagnostics.md#first-revit-launch-failed-cause-still-under-investigation) distinguishes the actual Revit failure from the successful external probe. The startup issue and the remaining live tests are still open.

After the person closed Revit, the agent confirmed normal exit and unchanged plugin and sample files. It then requested just one step: open Revit to its Home screen. Checking application startup before loading a model keeps the next observation specific enough to interpret.

The same error returned. This time the agent checked where Windows had actually stored the file, using its open file handle. Windows had redirected the agent's new AppData files into Codex's private cache while showing the ordinary folder name. Revit looked in the ordinary folder. The agent's earlier extra PowerShell process saw the same redirected view, so that check had not crossed the boundary that mattered.

Suggested follow-up prompt:

> Check whether both applications are accessing the same physical files, not just displaying the same path. Apply that finding to the other shared files, preserve recovery information, and prove the correction in the application that failed.

The agent added tests that reproduced this difference, moved the diagnostic controls to a shared user folder, and found that the installed MCP server needed a separate visibility correction too. The [technical investigation](../../projects/revit-readiness/docs/verification/2026-10-21-host-diagnostics.md#physical-path-investigation-established-the-cause) records both the correction and the remaining deployment work. Passing file hashes, another child process, and a successful build were useful checks, but none established that Revit or the other desktop application could see the same files.

The author then reported, “ready...no errors during loading.” The agent checked Revit's own startup journal and the trace Revit created in the corrected location. These observations verified the startup correction in Revit. The next instruction was simply to open the disposable model and start its bridge. The author handled those UI steps; the agent handled controlled requests and evidence. This kept the person's effort small while testing the boundary that had actually failed. The [startup result](../../projects/revit-readiness/docs/verification/2026-10-21-host-diagnostics.md#corrected-startup-verified-in-revit) remains separate from the later interruption tests and desktop acceptance.

## Ask what happened after the timeout

After the author confirmed the model was open and the bridge started, the agent paused two requests in controlled places. One was waiting just before reading the model; the other had already begun reading. Both timed out. The agent then released them and examined what happened inside Revit and what the connected client received.

The first request never began its model read. The second finished its already-started read but did not return a late success. A fresh check afterward still returned the expected model data. These results answer different questions from “did the client display a timeout?” The [technical record](../../projects/revit-readiness/docs/verification/2026-10-21-host-diagnostics.md#first-live-diagnostic-deadline-controls) keeps the evidence and remaining tests explicit.

Suggested participant prompt:

> Show what happened inside the application after the client timed out. Check both work that has not started and work already underway. Keep the client connected while you release the test pause, then prove that a fresh request still works. Tell me which other interruption cases remain untested.

The agent also deliberately damaged copies of the evidence to check that its comparison would reject them. Its first comparison assumed extra fields existed in the error result; the unmodified successful capture exposed that mistake. The agent corrected the comparison and kept the failed attempt. Participants should expect verification code to need verification too.

## Check that the interruption reached Revit

The author next said “please proceed.” The agent tested cancellation, a disconnected client, waiting requests, and Stop during a read. Before using the new test driver with Revit, it checked the driver against a disposable endpoint. That caught a misleading result: the client reported cancellation, but no cancellation message had reached the server. The agent kept that failed attempt, changed the test to send an explicit cancellation message through the official SDK, and verified the receiving side before proceeding.

Suggested participant prompt:

> Prove that the interruption reached the application, not just that the client stopped waiting. Separate cancellation, disconnect, timeout and Stop. Test waiting work and work already underway, preserve failed attempts, and show that the application can recover afterward.

Actual Revit traces then showed that canceled waiting work never entered the reader, while already-started work finished without returning late success. Stop released connections and removed its event hooks while a read was still held. The agent asked the person to start the bridge again to check recovery. These results and the still-unexplained token-only cancellation observation are kept separate in the [technical record](../../projects/revit-readiness/docs/verification/2026-10-21-host-interruptions.md). A successful explicit-cancellation test does not explain away a different failed stimulus.

## Question the test as well as the plugin

The author replied “started.” The agent verified that the new bridge session returned the same model information, then tested Stop with three requests waiting behind an active request. This exposed a mistake in the test: it paused Revit's application thread, then waited for cleanup that needed that thread to resume.

The agent inspected the actual plugin code and trace before changing anything. Network cleanup and canceled requests had progressed correctly. The final event-hook cleanup was designed to finish when Revit regained its application thread. The agent corrected the observer's waiting order, preserved the failed attempt, and asked for one more Start. The repeated capture then verified waiting work never ran and all required cleanup completed. The plugin itself did not need a patch.

Suggested participant prompt:

> When a test fails, check whether the plugin, the test, or the expectation is wrong. Show the evidence for your explanation before changing code. Make sure the test is not blocking the event it waits for, keep the failed attempt, and repeat the corrected test.

This applies the review lesson about execution and waiting to the agent's own verification tools. A reported failure deserves investigation; it does not automatically establish a product defect. The [technical record](../../projects/revit-readiness/docs/verification/2026-10-21-host-stop-recovery.md) separates fresh recovery, the failed observer, the successful repeat and what remains unverified.

## Change one thing at a time during setup

The author then reported “revit is closed.” The agent verified shutdown and saved files, restored the normal plugin, and addressed the server files that had been redirected into Codex's private cache. Its initial preflight found that current build folders contained different binaries. Deploying those at the same time would have mixed a location change with a build change.

The agent instead used the verified normal build, preserved its dependencies and notices, and installed it in a shared user folder with new recovery records. It also updated the installer default so a later installation would use that location. Startup checks passed for all three protocol revisions; actual use through both desktop applications remained a separate requirement.

Suggested participant prompt:

> Keep the tested build while correcting its installation location. Show that the binaries are unchanged, preserve recovery in the right filesystem context, and update the instructions so the next agent does not repeat the old setup. Then verify access from the applications that will actually use it.

The [technical record](../../projects/revit-readiness/docs/verification/2026-10-21-shared-server-installation.md) distinguishes preserved binaries, installer changes, SDK connection checks and desktop acceptance still to come.

The author's next **“ready”** confirmed the normal Revit model and bridge were running. The agent then used the relocated server to read the model and compared the entire answer with the earlier baseline: 16 examined elements, zero findings, complete coverage and no model changes. This is the next teaching distinction: a successful installation must be followed by a check from a consuming process. An SDK client provided that check here; Codex desktop and Claude Desktop still need their own demonstrations. See the [recorded follow-up](../../projects/revit-readiness/docs/verification/2026-10-21-shared-server-installation.md#normal-revit-follow-up).

## Test the way the application starts the server

Before desktop configuration, the agent found that the working harness used one fresh log folder per run, but a desktop may launch the same configured command more than once. Reusing that folder would stop the server from starting. The agent added tests with simultaneous launches and a reconnect, then added per-session capture folders. The existing refusal to overwrite evidence remains useful.

This extends the participant's question from “Did the command work?” to **“Will it work when the actual application reconnects?”** A suggested prompt is: “Test repeated and simultaneous launches using the exact client configuration. Preserve every capture, and make removal of our settings preserve my other connections.” This is guidance, not a quotation of an earlier author prompt.

When the author said they needed to close Revit and go to bed, the agent separated offline setup work from live acceptance. It verified Revit was closed, finished executable and configuration-recovery tests, and left actual desktop calls for the next session. Before stopping, the agent installed the tested external-server update while Revit was closed, preserving the working Revit add-in. Startup/discovery/error checks passed against the installed executable. It deliberately left a distinct next-session acceptance item: a passing offline launch is not a new live-model or desktop result. ## Prepare shutdown tests before asking the person to open Revit

After the sample demonstrations and starting guides, the author asked: **“Let's move on to the remaining shutdown and recovery checks. Prepare what you can with Revit closed, and tell me when you need me to open it. Keep recording the process in both teaching layers.”** This gives the agent a useful division of work: investigate, test and prepare recovery on its own; reserve a short, precise application action for the person.

The agent first investigated an intermittent test failure. That test expected a cancellation notification even when a waiting request had already finished and released its resources. It now tests finished waiting work separately from work still executing. The lesson is that a failed test deserves investigation too: neither changing the application to satisfy a mistaken test nor deleting the failure explains the evidence. The original failures and the corrected checks remain in the record.

The next test needs the person to close Revit normally while the agent records what happens to waiting requests. The diagnostic build briefly pauses that close sequence so the agent can inspect cleanup; it releases automatically if the observer fails. A real application close is still necessary. Offline tests cannot supply that result, and a test that holds Revit's main thread cannot pretend another operation runs on that same thread simultaneously.

Suggested participant prompt:

> Before asking me to open the application, explain exactly what this test can prove, prepare the recovery files and verify the observer. Give me the shortest reliable UI step. Keep failed attempts, and distinguish the test setup from the actual result.

The [preparation record](../../projects/revit-readiness/docs/verification/2026-10-22-shutdown-preparation.md) links the technical procedure and identifies what remains unverified. Checking backup files is useful preparation; actually restoring an installation is separate evidence.

The agent then installed the diagnostic host, restored the original files in a separate process, checked them, and installed the diagnostic candidate again. The author opened the sample and started the bridge. Only after a successful baseline and a ready observer did the agent ask the author to close Revit. Three waiting requests were rejected safely, their resources were released, and Revit exited normally.

The agent restored the normal host and asked for one final startup/read. Revit initially had no active bridge; the author said **“ok, I started the rediness bridge”**, after which the fresh check passed. This makes another useful distinction visible to participants: opening Revit and starting its bridge are separate actions. An agent should verify connection state and explain the next click, rather than keep retrying indefinitely or assume the installation is broken.

The [same record](../../projects/revit-readiness/docs/verification/2026-10-22-shutdown-preparation.md#normal-host-recovery-after-actual-shutdown) retains the unsuccessful connection attempts and successful recovery. This closes the observed queued-shutdown and normal-host-recovery sequence; it does not close every remaining acceptance question.
