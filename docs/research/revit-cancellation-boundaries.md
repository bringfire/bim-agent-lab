# Cancellation callback boundaries — 2026-10-21

Research prompted by the [independent Task 3 P1](../superpowers/reviews/revit-mcp-bridge/2026-10-21-task-3-deadline-review.md). Baseline `f79506d` used `CancellationTokenSource.CancelAfter` on a linked source. The reviewer reproduced an unhandled callback AggregateException on net48 and net10.0 timer threads. The endpoint's handlers were on a different execution path.

Microsoft documents that [Cancel() aggregates registered callback exceptions](https://learn.microsoft.com/en-us/dotnet/api/system.threading.cancellationtokensource.cancel?view=net-10.0); it also recommends callbacks not throw. Our conclusion is narrower than a guarantee about arbitrary third-party code: because this boundary lends its token to executors, it must contain exceptions raised while **it invokes** those callbacks. It cannot make every exception on every thread safe. In particular, registering a throwing callback on an already-canceled token executes on the registering caller; that caller needs its own exception boundary.

Microsoft's [Timer.Dispose documentation](https://learn.microsoft.com/en-us/dotnet/api/system.threading.timer.dispose?view=net-10.0) distinguishes disposal from completion of callbacks already queued or running. The implementing agent applied that ownership distinction to the replacement asynchronous deadline operation and to callbacks initiated by upstream/owner tokens. These are design inferences from the API contract, tested locally on both target runtimes.

The correction uses original project code: an owned asynchronous delay that rechecks the existing RequestBudget, explicit upstream/owner registrations into one contained cancellation method, active-callback accounting, and deferred disposal. No new library, copied SDK implementation, package upgrade, protocol change or global exception policy is involved. C# MCP SDK 2.2.0 remains package consumption; its already-attributed stdin helper is separate. TypeScript SDK 1.26.0 remains a learning precedent.

The reviewer-supplied reproducer is retained as attributed evidence in the [verification record](../../projects/revit-readiness/docs/verification/2026-10-21-deadline-cancellation.md), not incorporated into production code. The new regression harness is original project test code. This research does not establish live Revit or desktop acceptance.


## Follow-up: safety does not establish progress

The next independent review closed the deadline P1 but found held callbacks blocking actual stop/disconnect. The [execution/waiting model](../explanation/bridge-execution-and-waiting.md) was committed at 373e5a8 before correction. Microsoft documents synchronous callback execution in Cancel and a separate immediate-state/asynchronous-notification contract in modern CancelAsync; those official pages were rechecked on 2026-10-21. The application now makes its own immediate context state explicit for the shared net48/net10 API, isolates transport signaling and bounds retained endpoint notification work. This is original application logic, not a copied implementation of CancelAsync and not a new dependency. The [progress evidence](../../projects/revit-readiness/docs/verification/2026-10-21-cancellation-progress.md) includes actual endpoint and client paths; helper-only timer cases were insufficient.
