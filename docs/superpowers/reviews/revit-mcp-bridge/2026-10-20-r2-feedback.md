Reviewed plan revision 1 at `17108c239e3aa6f384c89f15d2fd623dbce60760` against approved spec revision 2.

1. **R2-01 — Major: carry cancellation and the established budget into the Revit executor.**
   [Task 4](../../../../docs/superpowers/plans/2026-10-20-revit-mcp-bridge.md) passes only `BridgeRequest` into its execution callback. [Task 5’s executor](../../../../docs/superpowers/plans/2026-10-20-revit-mcp-bridge.md) likewise receives neither cancellation state nor the established monotonic budget.

   **Failure scenario:** the queue checks cancellation, then the executor spends time reading and validating the sidecar. The caller cancels during that work, but the executor still invokes `RequiredInformationReader`. This misses the spec’s check **immediately before invoking the reader**.

   **Smallest correction:** define an execution context carrying the request, cancellation token, and existing budget through endpoint → queue → executor. Check it immediately before the reader and before publishing the result.

   **Verification:** pause execution during sidecar validation, separately cancel and expire the request, then resume. Assert zero reader invocations. Retain the separate test proving an already-running read may finish but cannot publish late success.

2. **R2-02 — Major: preserve the SDK’s Windows stdin cancellation handling.**
   [Task 1](../../../../docs/superpowers/plans/2026-10-20-revit-mcp-bridge.md) chooses `StreamServerTransport` with a transparent tracing wrapper. The pinned SDK’s `StdioServerTransport` additionally wraps standard input because console streams do not honor cancellation or cancel pending reads on disposal. Its general stream transport awaits the read loop during disposal. [Pinned stdio implementation](https://github.com/modelcontextprotocol/csharp-sdk/blob/6fa3825973949a9c4f0cd8af344e15a8db09dc35/src/ModelContextProtocol.Core/Server/StdioServerTransport.cs), [stream disposal implementation](https://github.com/modelcontextprotocol/csharp-sdk/blob/6fa3825973949a9c4f0cd8af344e15a8db09dc35/src/ModelContextProtocol.Core/Server/StreamServerTransport.cs).

   **Failure scenario:** standard input remains open and idle when host cancellation occurs; shutdown can hang awaiting the pending read. Tests using cancellation-aware memory streams or closing stdin would miss this.

   **Smallest correction:** explicitly retain cancellation-aware stdin behavior, either through the SDK stdio transport with suitable tracing or a documented adapter around the supplied stream. Record provenance if adapting SDK code.

   **Verification:** use a real Windows subprocess, keep stdin open without sending bytes, trigger host cancellation, and assert bounded shutdown with tracing both enabled and disabled—without relying on EOF or forced termination.

3. **R2-03 — Major: specify recovery from a partially applied installation.**
   [Task 7](../../../../docs/superpowers/plans/2026-10-20-revit-mcp-bridge.md) describes backup receipts and successful-install rollback, but does not define when recovery information becomes durable or how interrupted installation is recovered. The [existing installer](../../../../projects/revit-readiness/scripts/Install-Readiness.ps1) overwrites and deletes files before later fixture validation and synchronization.

   **Failure scenario:** installation replaces the readiness assembly, then fails copying another dependency or validating the fixture installation. A receipt saved only after success cannot restore the previous working installation; hashes alone cannot restore overwritten or deleted contents.

   **Smallest correction:** require complete preflight validation and durable backups/recovery records before the first mutation. Cover replaced **and deleted** files, manifests, inventories, and the optional fixture core/inventory. Define recovery for partial application.

   **Verification:** inject failures after a copy, obsolete-file deletion, and fixture synchronization. Recovery must restore prior owned contents and inventories while preserving unrelated files.

4. **R2-04 — Minor: reconcile instance-selection errors with the declared interface.**
   [Task 3](../../../../docs/superpowers/plans/2026-10-20-revit-mcp-bridge.md) declares `Resolve(...):BridgeSessionDescriptor`, while its example assertion accesses `.Error.Code`; the shared `BridgeException` appears only in Task 4.

   **Smallest correction:** choose a consistent typed-result or exception contract and define it before its first consumer. Also specify how unavailable/ambiguous selection reaches the MCP error mapping when no `PipeBridgeClient` can yet be constructed.

   **Verification:** test zero candidates and multiple candidates through the production startup/tool path, asserting the selected stable error behavior.

## Cross-cutting direction supplied by the author

The author's accompanying message connects the findings through operation lifetime and ownership. These exact excerpts are separate from the attached review:

> The common gap is reasoning about what remains safe when an operation stops halfway through.

> Walk each operation from admission through completion, including cancellation, timeout, disconnect, shutdown, and partial failure. For every stage, identify who owns the resources, which conditions must still hold before the next action, and how the system reaches a safe final state. Carry those responsibilities into the interfaces and test failures at the transitions.

The drafting agent accepts this diagnosis after inspecting the signatures, pinned SDK stdio/stream implementations, and current installer. Revision 1 checked individual task coverage but did not carry every lifetime guarantee across task boundaries. “Check cancellation” and “save a receipt” were insufficient without specifying where that state remains available and when recovery data already exists.
